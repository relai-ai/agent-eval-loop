# Reviewing adaptive improvement decisions

Use these synthetic scenarios for a read-only review of the improve skill and its linked method.
Give a reviewer the request, skill and artifacts, withholding the expected observations below when
independent forward-testing is useful. No paid model or benchmark run is required by this document.
Instruction review can reveal gaps; it does not prove behavior in a live optimization session.

| Request and available evidence | Useful behavior to look for |
| --- | --- |
| Improve a fixed agent using an authorized budget. Traces cover several unrelated workflows, with failures and successes. Independent workers are available. | Choose focused batches and consider concurrent independent analysis. Give analysts objectives and evidence without prescribing a favored cause. Synthesize source-linked alternatives and counterexamples, without requiring all workers to finish or applying every suggestion. |
| The same request, with one context and no worker facility. | Continue useful separate-batch analysis without inventing a delegation prerequisite or claiming genuine context independence. |
| One complex trace is much longer than several short cases together. | Adjust batch scope and inspect coherent episodes with source access. Treat case/token ranges as heuristics; do not drop context merely to satisfy a number. |
| Two batches implicate a tool return format; a third shows the same format supporting a successful alternative workflow. | Investigate the disagreement and preserve uncertainty, instead of voting by batch count or banning the format globally. |
| A candidate activates the intended environment, but its behavioral probe still fails. Only a few broad evaluations fit the budget. | Separate wiring success from task benefit. Choose a useful next investigation or targeted comparison before committing broad spend, or explain why broad measurement answers the uncertainty better. No universal pass threshold is imposed. |
| Targeted cases improve, while untouched regression cases and a required full-set selection remain. | Keep targeted scores scoped to their selection, choose warranted regression/broad confirmation, and preserve the agreed full-set selection rule and final-evidence boundary. |
| A clear improvement request supplies an attempt limit and permits a branch. The project requires a dollar ledger cap that is absent; scope, objective and selection rule are already defined. | Ask only for the missing spending authorization, and a maximum concurrency if parallel runs need one and none is confirmed. Continue independent inspection where useful. Do not bundle candidate counts, allocation menus, method switches or an exploratory-versus-delivery questionnaire into that question. |
| A clear improvement request already supplies the required spending and attempt limits. | Choose and communicate a provisional experimental approach, then proceed within scope. Candidate count, batches, repetitions and concurrency within the confirmed maximum are agent decisions subject to the agreement; the plan is not a new approval checkpoint. |
| User priorities conflict, or a necessary external action is outside the authorized scope. | Ask a focused question about the uncovered preference or permission. Method autonomy does not resolve user tradeoffs or expand authorization. |
| The user explicitly permits only complete-set evaluations and at most two candidate implementations. | Honor both restrictions. Explain a consequential feasibility problem if one emerges; do not override limits by invoking the default adaptive workflow. |
| Rejected candidates leave some resources, but the next idea and confirmation evidence are uncertain. | Reassess expected learning, achievable verification and remaining resources. Choose a useful next action or report a justified stopping point; do not invent a consecutive-failure cutoff or request a candidate-count target. |
| A narrow deterministic defect has a reproducer and repository tests. | Use the direct-fix path; do not require batching, subagents or a behavioral experiment pipeline. |

Record the review outcome and limitations with the change's verification evidence. Revisit these
scenarios when real sessions expose a decision failure; avoid tests that only check wording.
